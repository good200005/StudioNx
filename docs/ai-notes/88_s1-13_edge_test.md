## 2. 무엇을 바꿨나

| 파일 | 내용 |
|---|---|
| `docs/handoff/p1-28_tests/lib.mjs` | 시험이 띄우는 브라우저를 환경 변수 `BROWSER_PATH`로 고를 수 있게 했습니다 (없으면 기존 Chrome) |
| `studionx/tests/audio/lib/runner.mjs` | 오디오 회귀 테스트도 `BROWSER_PATH`를 읽습니다 (예전 이름 `CHROME_PATH`도 됨) |
| `studionx/tests/audio/README.md` | 위 사용법 추가 |
| `docs/handoff/s1-13_tests/run_browser_suite.ps1` | 15개 시험을 순서대로 돌려 표로 보여 주는 묶음 실행기. 시험마다 제한 시간(기본 240초)을 두어 하나가 멈춰도 뒤의 시험이 막히지 않습니다 |

Edge에서 돌리는 방법입니다 (저장소 맨 위, 시험용 서버 8001이 떠 있어야 화면 시험이 돕니다).

```powershell
$env:BROWSER_PATH = 'C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe'
powershell -File docs/handoff/s1-13_tests/run_browser_suite.ps1
```

## 3. 왜 이렇게

| 선택 | 이유 |
|---|---|
| 시험을 새로 만들지 않고 기존 시험을 그대로 돌렸습니다 | 브라우저가 달라도 앱이 같은 동작을 하는지가 질문이므로, 같은 시험이 같은 결과를 내는지가 가장 직접적인 답입니다. |
| 브라우저 선택을 환경 변수로 했습니다 | 시험 14개를 하나하나 고치지 않고 띄우는 곳 두 군데만 고치면 됩니다. 기본값은 그대로 Chrome이라 기존 사용법이 바뀌지 않습니다. |
| 묶음 실행기에 시간 제한을 뒀습니다 | 오래된 S1-09 시험이 멈추는 것을 겪었습니다(87). 한 시험이 멈추면 묶음 전체가 막히므로, 제한 시간이 지나면 그 시험의 프로세스와 브라우저를 정리하고 다음으로 넘어갑니다. |
| 오디오 회귀 테스트의 골든을 Edge용으로 따로 만들지 않았습니다 | Chrome의 골든과 Edge의 렌더링이 사실상 같아서 골든 하나로 충분합니다. 브라우저마다 골든이 필요해지면 그때 나눕니다. |
| S1-09 시험은 처음에 묶음에서 뺐다가 고친 뒤 넣었습니다 | 고치기 전에는 Chrome에서도 실패하고 멈추는 시험이라(87) 브라우저 차이를 가려내는 데 쓸 수 없었습니다. 이 문서의 §5에서 고친 내용을 설명합니다. |

## 4. 알려진 한계

| 한계 | 내용 |
|---|---|
| Edge와 Chrome이 같은 엔진입니다 | 둘 다 Chromium 155 계열입니다. 그래서 소리 계산이 같게 나오는 것은 당연한 면이 있고, 이 시험은 "Edge에서도 앱이 문제없이 동작한다"는 확인이지 서로 다른 오디오 엔진을 비교한 것이 아닙니다. Firefox와 Safari는 범위에서 뺐습니다. |
| 헤드리스로만 시험했습니다 | 화면은 실제 창이 아니라 헤드리스 렌더링이고, 스피커로 나오는 소리는 듣지 않았습니다. 재생 소리의 크기와 모양은 분석기로 확인했습니다. |
| Edge의 확장과 설정은 쓰지 않았습니다 | 시험은 빈 프로필로 돌립니다. 사용자의 Edge에 설치된 확장(광고 차단 등)이 앱에 끼치는 영향은 시험하지 않았습니다. |
| 자동 실행이 아닙니다 | 사람이 묶음 실행기를 돌려야 합니다. 저장소에 CI가 생기면 한 줄로 연결할 수 있습니다. |

## 5. 오래된 S1-09 화면 시험을 고친 일

템포 변경(87)에서 S1-09 화면 시험(`docs/handoff/s1-09_tests/ui.mjs`)이 2건 실패한 뒤 멈추는 것을 발견했고, 이번에 고쳤습니다. 이제 40건이 통과하고, 두 번 연달아 돌려도 같은 결과이며, Edge에서도 통과합니다.

| 문제 | 원인 | 고침 |
|---|---|---|
| 시험이 멈춤 | 이 시험은 화면을 이동할 때 `Page.navigate`만 불렀습니다. 그 뒤 S1-10에서 자동 저장이 생겼고, 저장하지 않은 변경이 있는 채로 페이지를 떠나면 브라우저가 "떠나시겠습니까?" 창(`beforeunload`)을 띄웁니다. 헤드리스에서는 이 창을 누를 사람이 없어서 이동이 끝나지 않았습니다. | 창이 뜨면 수락하는 이동 함수(`nav`)를 썼습니다. S1-11 이후의 시험이 쓰던 방식과 같습니다. |
| "CONNECT 칸은 S1-10 안내" 실패 | 예전에는 Connect 칸에 "S1-10에서 구현" 안내 문구가 있었는데, S1-10a에서 Connect가 구현되어 선택 칸(None, Connected)과 Track 입력으로 바뀌었습니다. | 기대를 현재 화면에 맞췄습니다 (선택 칸의 값과 Track 입력이 있는지 확인). |
| "모달에서 바꾼 값이 서버에 저장됨" 실패 | 시험이 모달의 첫 노브를 늘 위로 45픽셀 끌었습니다. 컴프레서의 첫 노브(Threshold)가 이미 최댓값 0이라 위로 끌어도 값이 변하지 않았습니다. 앞선 실행이 값을 최댓값으로 남겨 두어서, 시험 결과가 직전 실행의 상태에 좌우되었습니다. | 노브의 현재 값이 중간보다 높으면 아래로, 아니면 위로 끌도록 했습니다 (볼륨 시험이 이미 쓰던 방식). |

앱 코드의 오류는 없었고 모두 시험의 문제였습니다. 87에서 "이번 변경 때문이 아니라 시험이 오래되었다"고 판단한 것이 맞았습니다.

## 7. 자주 받을 질문 대비 (Q/A)

**Q. Edge에서 앱이 Chrome과 똑같이 동작하나요?**
A. 시험 15개(합 379건, 오디오 회귀 테스트는 5개 프로젝트로 셈)가 모두 통과했습니다. 소리 계산, 화면 조작, 저장과 불러오기, 내보내기, 템포 변경을 포함합니다. 오디오 회귀 테스트에서는 Edge의 렌더링이 Chrome의 골든과 사실상 같았습니다(차이가 -160 dBFS 안팎).

**Q. 왜 Firefox와 Safari는 안 보나요?**
A. 사용자가 범위를 Chrome과 Edge로 정했습니다 (2026-10-21). 두 브라우저는 오디오 엔진이 달라서 시험하면 새로운 차이가 나올 수 있지만, 이번 MVP의 범위에서는 뺐습니다.

**Q. 앞으로 브라우저를 올리면 어떻게 하나요?**
A. 묶음 실행기로 같은 시험을 돌립니다. 오디오 회귀 테스트의 차이가 허용 오차(-80 dBFS) 근처로 올라오면 그때 골든을 다시 만들고 변경 기록에 브라우저 버전을 남깁니다 (86).
