## 1. 점검에서 알게 된 것

Sentry 오류 정리를 하려고 먼저 Sentry가 어디까지 연결되어 있는지 보았습니다.

| 영역 | 점검 전 상태 |
|---|---|
| 백엔드 | 연결되어 있었습니다. `core/sentry.py`가 서버용 DSN이 있으면 켜지고, 비밀번호, 토큰, 쿠키를 지웁니다. |
| 프런트 | 연결되어 있지 않았습니다. `sentry-init.js`는 `TODO`만 있는 빈 템플릿이었고, 어느 페이지도 불러오지 않았으며, 전역 오류 처리(`window.onerror`, `unhandledrejection`)도 없었습니다. |
| 개인정보 처리방침 | 브라우저 오류도 Sentry로 보낸다고 적혀 있었습니다. 구현이 문서와 맞지 않았습니다. |

소리 계산, 재생, 내보내기 같은 핵심 기능은 전부 화면에서 돌기 때문에, 이 빈칸이 가장 컸습니다. Sentry에 오류가 없다면 그것은 "오류가 없어서"가 아니라 "수집하지 않아서"였습니다.

## 2. 실행 결과

가짜 Sentry 서버를 두고 실제 화면(헤드리스 Chrome)에서 오류를 일부러 냈습니다. 주소는 `home.html?token=URLSECRET#access_token=HASHSECRET`였습니다.

| 확인한 장면 | 결과 |
|---|---|
| 페이지를 열기만 함 | 요청이 하나도 없음 |
| 잡히지 않은 오류, Promise 거절, 같은 자리에서 두 번 나는 오류 | 3건만 감 (반복은 한 번) |
| 서버가 준 오류(`ApiError`), 브라우저의 `ResizeObserver` 알림 | 가지 않음 |
| 보낸 내용 전체 | 주소의 `URLSECRET`, `HASHSECRET`, 문구의 이메일과 `token=` 값이 모두 없음 |
| 요청 헤더 | 쿠키, 인증 헤더, Referer 없음 |
| 오류 30개를 쏟아냄 | 10건에서 멈춤 |
| 로그인한 상태로 8개 페이지를 엶 | 모두 오류 처리기가 설치됨 |
| 화면용 DSN이 비어 있는 서버 | 오류가 나도 아무것도 보내지 않음 |
| 진짜 Sentry로 이벤트 한 건을 보냄 (사용자 허락, 같은 날) | 응답 `200`과 `{"id":"4bcecb3d7ab8bbad75f20eca00cd1a62"}`를 받았고, 이 번호는 보낸 이벤트의 번호와 같습니다. 오류 문구는 `S1-13 Sentry connectivity test: safe to ignore`입니다. |

진짜 Sentry 시험은 브라우저용 DSN이 아직 없어서 `.env`의 서버용 DSN을 시험 프로세스의 환경 변수로만 빌려 썼습니다(파일은 바꾸지 않고 값도 출력하지 않음). 그래서 이 이벤트는 서버용 프로젝트에 들어가 있습니다. 서버 쪽에서 같은 이벤트가 이중으로 가지 않게, 시험이 띄운 앱 서버의 서버용 DSN은 비웠습니다. 다시 하려면 `node docs/handoff/s1-13_tests/send_real_sentry.mjs`를 씁니다(브라우저용 DSN은 환경 변수 `SENTRY_BROWSER_DSN`, 아직 없으면 `--use-server-dsn`).

## 5. 왜 이렇게 (이번 작업의 결정)

| 결정 | 이유 |
|---|---|
| Sentry의 브라우저 스크립트(SDK) 대신 직접 보냅니다 | 앞서 SDK를 CDN에서 불러오는 방식으로 설명드렸지만 바꿨습니다. 처리방침이 "비밀번호, 토큰, 쿠키는 보내기 전에 지웁니다"라고 약속하는데, 이 파일 하나에서 나가는 내용을 모두 확인할 수 있고, 외부 스크립트를 모든 페이지에 싣지 않으며, 버전과 무결성 해시를 따로 관리하지 않아도 됩니다. 대신 이동 경로, 성능 측정, 소스맵은 없습니다 (이 프로젝트는 번들링 없이 원본을 올려서 소스맵이 필요 없음). |
| 서버가 DSN을 내려 줍니다 | 화면 코드에 적으면 환경마다 파일을 고쳐야 합니다. 서버의 설정 한 곳에서 켜고 끌 수 있습니다. |
| 기본은 꺼져 있습니다 | DSN을 설정하기 전에는 아무것도 나가지 않습니다. 개발 중이나 시험 중에 진짜 Sentry로 가는 일이 없습니다. |
| 브라우저용 프로젝트를 서버용과 나눕니다 | Python 오류와 JS 오류가 섞이지 않고, 브라우저 오류가 많아도 서버 오류가 묻히지 않습니다 (강제는 아님). |
| 서버가 일부러 준 오류(`ApiError`)는 보내지 않습니다 | 로그인이 풀리거나 입력이 잘못된 것은 정상 동작입니다. 서버의 5xx는 서버 쪽 Sentry가 받습니다. |
| 한 화면에서 10건까지, 같은 오류는 한 번만 | 반복문 안의 오류가 Sentry를 쏟아붓지 않게 합니다. |
| 페이지마다 첫 `import`로 둡니다 | 다른 파일을 불러오다 난 오류도 잡으려면 이 파일이 가장 먼저 실행되어야 합니다. |
| 빈 `catch` 점검은 이번에 하지 않았습니다 | 3가지 중 1번(연결)만 승인받았습니다. 점검에서 본 숫자(§7)는 참고로 남깁니다. |

## 6. 시험 중에 발견해서 고친 문제

| 문제 | 원인 | 고침 |
|---|---|---|
| "같은 오류는 한 번만" 시험 실패 | 같은 문구의 `new Error('first')`를 두 줄에서 만들었더니 두 번 보내졌습니다. 난 자리(파일, 줄, 칸)가 달라서 다른 오류로 본 것이고 구현이 맞습니다. | 시험을 한 오류 객체를 두 번 보내는 것으로 고치고, "문구가 같아도 난 자리가 다르면 다른 오류"를 별도로 확인합니다. |
| 화면 시험에서 로그인이 422 | 시험이 로그인 본문을 객체 그대로 넣어서 서버가 거부했습니다. 다른 시험은 문자열로 한 번 더 감쌉니다. | 같은 방식으로 맞췄습니다. |
| 시험이 실제 Sentry로 새는 일 | 앱 서버가 `.env`의 서버용 DSN을 읽으면 시험 중 난 서버 오류가 진짜 Sentry로 갑니다. | 새 시험이 띄우는 서버와 8001 서버는 `SENTRY_DSN`과 `SENTRY_BROWSER_DSN`을 비워서 띄웁니다. 묶음 실행기의 사용 설명에도 적었습니다. (이전 시험에서 8001 서버를 이 설정 없이 띄운 적이 있지만 서버 오류가 나지 않아 실제로 간 것은 없다고 판단합니다. 확인한 것은 아닙니다.) |

앱 코드의 오류는 없었습니다.

## 7. 켜는 방법과 알려진 한계

### 켜는 방법

1. Sentry에서 새 프로젝트를 만듭니다. 플랫폼은 Browser JavaScript를 고릅니다 (서버용과 다른 프로젝트).
2. 프로젝트 설정의 Client Keys에서 DSN을 복사합니다.
3. `studionx/.env`에 `SENTRY_BROWSER_DSN=복사한 DSN`을 적고 서버를 다시 띄웁니다.
4. 브라우저에서 화면을 열고 개발자 도구 콘솔에 `setTimeout(function () { throw new Error('sentry test'); })`를 입력합니다.
5. Sentry 프로젝트에 오류가 나타나는지 확인합니다 (몇 초 걸릴 수 있음).

### 한계

| 한계 | 내용 |
|---|---|
| Sentry 화면의 표시는 확인하지 못했습니다 | 실제 Sentry가 받았다는 응답(`200`과 이벤트 번호)까지는 확인했지만, Issues 목록에서 제목, 스택, 태그가 어떻게 보이는지는 제가 볼 수 없습니다. 위 4단계나 이벤트 번호로 직접 확인해 주세요. 안 보이면 개발자 도구 네트워크 탭의 `envelope` 요청 응답을 보면 원인이 나옵니다. |
| 이동 경로, 성능 측정, 소스맵이 없습니다 | 위 §5에서 의도한 것입니다. |
| 오프라인에서 난 오류는 사라집니다 | 전송 실패를 다시 시도하지 않습니다. |
| 삼켜진 오류는 보이지 않습니다 | 점검에서 프런트의 빈 `catch`가 20건(12개 파일), 빈 `.catch` 핸들러가 4건 있었습니다. 대부분 오디오 노드를 멈출 때 "이미 끝났음"을 무시하는 의도적인 처리로 보이지만 하나씩 확인하지는 않았습니다. |
| Edge, Chrome만 시험했습니다 | Edge에서도 같은 시험이 통과하는지는 묶음 실행기로 확인합니다 (88). |

## 9. 자주 받을 질문 대비 (Q/A)

**Q. 사용자의 개인정보가 Sentry로 나가나요?**
A. 이메일, 토큰, 비밀번호, 쿠키, 주소의 query는 나가지 않습니다. 나가는 것은 오류 종류와 문구(비밀을 지운 뒤), 호출 스택, 페이지 경로, 브라우저 종류, 환경과 버전입니다. Sentry는 요청을 받으면서 IP 주소를 알게 되며, 이는 개인정보 처리방침에 적혀 있습니다.

**Q. 왜 Sentry의 공식 스크립트를 안 쓰나요?**
A. 나가는 내용을 이 프로젝트의 파일 하나에서 모두 확인하고 통제하려고 했습니다. 외부 스크립트를 모든 페이지에 싣지 않는 장점도 있습니다. 이동 경로나 성능 측정이 필요해지면 공식 스크립트로 바꿀 수 있습니다 (313 §2).

**Q. 켜 두면 화면이 느려지나요?**
A. 오류가 없으면 요청이 하나도 늘지 않고, 처리기를 설치하는 비용은 무시할 수준입니다. 오류가 났을 때만 설정을 한 번 읽고 요청을 보냅니다.

**Q. 오류가 수천 번 반복되면 어떻게 되나요?**
A. 같은 오류는 한 번만, 한 화면에서 최대 10건까지만 보냅니다. 새로고침하면 다시 시작하므로 사용자가 계속 새로고침하면 그만큼 갈 수는 있습니다.

**Q. 서버 오류는 어디로 가나요?**
A. 그대로 서버용 DSN(`SENTRY_DSN`)의 프로젝트로 갑니다. 이번 작업은 서버 쪽을 바꾸지 않았습니다.
