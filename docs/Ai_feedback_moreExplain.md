## 1. 상황 인지 팁 (제안 3.2)

### 1.1 한 줄 정의
> 사용자가 **묻기 전에**, Nyxi가 작업 상태를 보고 "이거 문제일 수 있어요"를 **먼저** 알려주는 기능입니다.

지금 적용된 Nyxi 도우미는 **질문해야 답하는(수동)** 방식입니다. 상황 인지 팁은 **먼저 말 거는(능동)** 방식이라, 유용할 수도 있지만 **잔소리처럼 느껴질 위험**이 있습니다. 그래서 애매하게 느끼시는 게 자연스럽습니다.

### 1.2 구체적인 예시
| # | 상황 (감지 조건) | Nyxi 말풍선 예시 | 버튼 |
|---|---|---|---|
| 1 | **마스터 클리핑** — 재생 중 마스터 피크가 0 dBFS 초과 3회 이상 | "마스터에서 소리가 깨지고 있어요(클리핑). 마스터 볼륨을 -3dB 낮추거나 리미터를 넣어볼까요?" | [리미터 추가] [볼륨 -3dB] [괜찮아요] |
| 2 | **트랙 클리핑** — 특정 트랙 미터가 계속 빨간색 | "Kick 트랙이 너무 커서 찌그러져요." | [게인 -6dB] [무시] |
| 3 | **저역 겹침** — Kick과 Bass가 같은 저역대(50~100Hz)에서 동시에 강함 | "킥과 베이스가 저음에서 부딪혀요. 베이스에 사이드체인 컴프를 걸면 킥이 또렷해져요." | [사이드체인 설정 열기] [설명 보기] |
| 4 | **음량 목표 벗어남** — 출력 직전 측정 LUFS가 -8보다 큼 | "지금 곡이 꽤 커요(-7 LUFS). 스트리밍 기준(-14)에선 자동으로 줄어들어요." | [마스터링 추천 보기] [그대로 출력] |
| 5 | **스케일 밖 음** — 키를 C minor로 정했는데 스케일 밖 노트가 다수 | "스케일 밖 음이 8개 있어요. 의도한 거라면 무시하세요!" | [스케일 밖 노트 선택] [무시] |
| 6 | **빈 트랙 출력** — 출력하려는데 소리가 없는 구간이 앞에 4마디 이상 | "곡 앞에 4마디가 비어 있어요. 출력 범위를 조정할까요?" | [범위 조정] [그대로] |
| 7 | **CPU 과부하** — 오디오 언더런(끊김) 연속 발생 | "소리가 끊기고 있어요. 리버브가 많은 트랙을 바운스(오디오로 굳히기)하면 가벼워져요." | [가장 무거운 트랙 보기] |
| 8 | **저장 안 함** — 30분 이상 저장 안 됨 + 자동 저장 꺼짐 | "30분째 저장 안 했어요!" | [지금 저장] |
| 9 | **용량 임박** — 저장 용량 90% 초과 | "저장 공간이 거의 찼어요." | [용량 정리] |

> 예시 1·2·7·8·9는 **규칙(숫자 비교)** 만으로 판단되어 AI 비용이 들지 않습니다. 3·4는 오디오 분석(주파수·LUFS)이 필요하고, 5·6은 프로젝트 데이터만 보면 됩니다. 즉 **대부분은 LLM 없이 구현**됩니다. 말풍선 문장만 템플릿으로 준비하면 됩니다.

### 1.3 잔소리가 되지 않게 하는 장치 (적용한다면 필수)
| 장치 | 내용 |
|---|---|
| 레벨 설정 | **끄기 / 중요한 것만(기본) / 모두**. "중요한 것만" = 클리핑·용량·저장처럼 결과물이나 데이터에 영향 있는 것 |
| 타이밍 | 재생 중이거나 드래그 중에는 말하지 않고, **재생을 멈췄을 때** 표시. 녹음 중에는 절대 표시 안 함 |
| 빈도 제한 | 같은 팁은 프로젝트당 1회(또는 24시간 1회), 전체 팁은 10분에 최대 1개 |
| 다시 보지 않기 | 팁마다 [이 팁 다시 보지 않기] |
| 조용한 표시 | 말풍선 대신 Nyxi 아이콘에 작은 점(●)만 찍고, 클릭하면 보여주는 "조용한 모드" |
| 튜토리얼과 연결 | 처음 몇 번은 팁에 [왜 그런가요?] 버튼 → 짧은 설명(학습 효과) |

### 1.4 장단점
| 장점 | 단점 / 위험 |
|---|---|
| 입문자는 "무엇이 문제인지"조차 모름 → 질문형 도우미만으로는 한계 | 숙련자에게는 방해. 끄기 옵션이 없으면 이탈 요인 |
| 대부분 규칙 기반이라 AI 비용 거의 없음 | 감지 규칙이 틀리면(오탐) 신뢰도 하락 |
| Nyxi 캐릭터가 "살아 있는" 느낌 → 캐릭터 존재 이유 강화 | 규칙마다 테스트 필요 → 구현·유지 비용 |
| Sentry 지표(언더런 등)와 같은 데이터를 재사용 가능 | 협업 중엔 "누구에게" 말할지 정해야 함 (예: 해당 트랙 담당자에게만) |

### 1.5 추천안
- **결론: "조용한 기본값 + 작게 시작"으로 적용하는 것을 추천합니다.**
  1. 3단계(Nyxi 캐릭터·도우미 구현 후)에 **규칙 4개만**: ① 마스터 클리핑 ② 트랙 클리핑 ③ 저장 안 함 ④ 용량 임박
  2. 기본값은 **"중요한 것만" + 재생 멈췄을 때만**
  3. 반응이 좋으면 v1.0 이후 저역 겹침·LUFS·스케일 밖 음 같은 "작곡 조언형" 팁 추가
- 결정 선택지:

| 선택 | 내용 |
|---|---|
| A (추천) | 위 추천안대로 3단계에 최소 규칙 4개로 적용 |
| B | 보류 — Nyxi 도우미(질문형)만 먼저 운영해 보고 v1.0 이후 재검토 |
| C | 적용하지 않음 |

## 2. 버전 스냅샷 · 복원 (제안 4.2)

### 2.1 왜 필요한가 — Undo·변경 이력과 무엇이 다른가
| 구분 | Undo/Redo | 변경 이력 (`project_change_logs`) | **스냅샷** (`project_snapshots`) |
|---|---|---|---|
| 단위 | 내 명령 하나씩 | 모든 사람의 연산 하나씩 | **프로젝트 전체 상태 통째로** |
| 범위 | 현재 브라우저 세션 (새로고침하면 사라짐) | 영구 | 영구 |
| 되돌리기 | 마지막부터 한 단계씩 | 직접 되돌리기 어려움 (연산 수천 개를 역으로 적용해야 함) | **한 번에** 특정 시점으로 |
| 협업 | 내 것만 | 기록용 | 모든 멤버에게 동시에 적용 |
| 비유 | 키보드의 Ctrl+Z | 블랙박스 기록 | 게임의 **세이브 파일** |

> 즉 Undo는 "방금 실수 되돌리기", 스냅샷은 "**어제 버전이 더 좋았어** → 그 상태로 돌아가기 / 나란히 비교하기"입니다.

### 2.2 이런 상황에서 씁니다
1. **믹스 실험**: "믹스 v1" 저장 → 과감하게 EQ·컴프 바꾸기 → 별로면 v1로 복원
2. **AI 추천 일괄 적용 후 후회**: 적용 직전 자동 스냅샷(`BEFORE_AI_APPLY`)으로 즉시 복원
3. **협업 사고**: 다른 멤버가 실수로 트랙 여러 개를 지움 → 어제 자동 스냅샷으로 복원
4. **버전 비교**: 스냅샷을 **새 프로젝트로 복제**해 v1과 v2를 탭 두 개로 열어 비교
5. **클라이언트 피드백**: "2주 전 버전으로 해 주세요" → 미리듣기로 확인 후 복원

### 2.3 언제 만들어지나
| 종류 (`snapshot_type`) | 만드는 시점 | 만드는 사람 |
|---|---|---|
| `MANUAL` | [스냅샷 저장] 버튼 + 이름 입력 | 사용자 (OWNER/EDITOR) |
| `AUTO_DAILY` | 하루 1회, 그날 변경이 있었을 때 (예: 새벽 4시 배치) | 서버 |
| `BEFORE_RESTORE` | 다른 스냅샷으로 복원하기 직전 | 서버 |
| `BEFORE_TEMPLATE` | 템플릿 **교체** 적용 직전 | 서버 |
| `BEFORE_AI_APPLY` | AI 추천 **일괄** 적용 직전 | 서버 |

### 2.4 무엇이 저장되나
```
project_snapshots (DB 행: 목록·메타 정보)
 └─ data_path → storage/snapshots/{project_id}/{snapshot_id}.json.gz   ← 실제 내용
      {
        "project":  { bpm, 박자, key, scale, master_settings },
        "tracks":   [ ...트랙, 디바이스(params), 연결선, 오토메이션 레인·포인트 ],
        "patterns": [ ...패턴, 노트 ],
        "clips":    [ ...클립 (sample_id 참조만) ],
        "scenes":   [ ... ]
      }
```
- **샘플 오디오 파일은 복사하지 않습니다.** `sample_id`로 참조만 하므로 스냅샷 하나는 보통 수십 KB ~ 수 MB입니다.
- 대신 **스냅샷이 참조하는 샘플은 실제 파일을 지우지 않습니다**(소프트 삭제 후에도 보존). 참조하는 스냅샷이 모두 정리되면 그때 파일 삭제 (FR-669).
- 코멘트·채팅·멤버 정보는 스냅샷에 포함하지 않습니다(작업 내용만).

### 2.5 복원은 이렇게 동작합니다
```
[사용자] 스냅샷 "믹스 v1" → [복원] 클릭
   │
   ▼
확인창: "현재 상태를 자동 저장한 뒤 '믹스 v1'(9/14 21:03)로 되돌립니다.
        접속 중인 멤버 2명의 화면도 함께 바뀝니다."  [복원] [취소]
   │ 복원
   ▼
서버 ① 현재 상태 → BEFORE_RESTORE 스냅샷 생성   ← 복원도 되돌릴 수 있게
     ② 프로젝트 데이터를 스냅샷 내용으로 교체 (트랜잭션)
     ③ projects.revision +1, change_log에 project.restore 기록
     ④ WebSocket으로 모든 접속자에게 project_restored 전송
   │
   ▼
[모든 접속자] 전체 상태 다시 로드 → 같은 화면, Undo 이력은 초기화
```
- 복원 권한: OWNER / EDITOR (VIEWER 불가)
- 복원 중 다른 멤버가 보낸 편집 연산은 revision이 맞지 않아 거부되고, 그 멤버 화면은 복원된 상태로 다시 로드됩니다.
- 다른 선택지 **[새 프로젝트로 복제]**: 원본은 그대로 두고 스냅샷 상태로 새 프로젝트를 만듭니다. 위험이 없어 "비교만 하고 싶을 때" 추천.

### 2.6 미리듣기
- 스냅샷 목록에서 ▶ 누르면 그 시점 상태를 **서버(또는 브라우저)에서 오프라인 렌더링**해 앞 30~60초(또는 루프 구간) 미리듣기를 만듭니다.
- 처음 한 번만 생성하고 `preview_path`에 저장해 재사용합니다. 렌더러는 Phase 3 출력 엔진을 그대로 씁니다.

### 2.7 보관 규칙 (자동 정리)
| 종류 | 보관 |
|---|---|
| `MANUAL`, 고정(📌) | 직접 지울 때까지 |
| `AUTO_DAILY` | 최근 7일은 매일 1개, 그 이전 4주는 주 1개만 남기고 정리 |
| `BEFORE_*` | 30일 후 정리 |

예) 오늘이 10/30이면 → 10/24~10/30 일일 7개 + 10/23 이전 4주간 주간 4개 = 자동 스냅샷 최대 11개 + 수동 스냅샷.
스냅샷 파일 크기는 저장 용량(PRD 01 §4.4)에 포함되어 대시보드에 "스냅샷" 항목으로 표시됩니다.

### 2.8 화면 예시
```
┌ 스냅샷 ──────────────────────────────── [+ 스냅샷 저장] ┐
│ 📌 믹스 v2            수동   멤버A  10/30 14:20   ▶ ⋯   │
│    믹스 v1            수동   나     10/28 21:03   ▶ ⋯   │
│    AI 적용 전          자동   -      10/28 20:55   ▶ ⋯   │
│    10/27 자동          자동   -      10/27 04:00   ▶ ⋯   │
│                         ⋯ → [복원] [새 프로젝트로 복제] [이름 변경] [고정] [삭제] │
└─────────────────────────────────────────────────────┘
```

## 3. AI 도우미 · 캐릭터 이름 추천 (Gopher 대체)

### 3.1 원칙
- **캐릭터와 도우미는 같은 이름**으로 합니다. 캐릭터가 도우미의 얼굴이므로 "Nyxi가 춤추고, Nyxi에게 묻는다"처럼 하나의 인격이 됩니다.
- 서비스명 **Studio Nx**와 연결되고, 한국어·영어 모두 부르기 쉬운 2~3음절.
- 확정 전 **상표 검색**(한국 KIPRIS, 미국 USPTO)과 도메인·SNS 계정 확인이 필요합니다. 아래 표의 "주의"는 일반적으로 알려진 충돌 가능성일 뿐, 법적 검토가 아닙니다.

### 3.2 후보 (검토 기록 — 1차 추천은 Nexi였고, 최종 결정은 §3.3)
| 순위 | 이름 | 읽기 | 의미 / 연상 | 장점 | 주의 |
|---|---|---|---|---|---|
| 1 | **Nexi** | 넥시 | **N**x + **ex**pert/**Ne**xt + 친근한 -i | 서비스명과 바로 연결, 귀여운 캐릭터 이름 느낌, 짧음 | 비슷한 이름의 소규모 서비스 존재 여부 확인 |
| 2 | **Nyx** | 닉스 | Studio **Nx** 발음과 거의 같음, 그리스 신화 밤의 여신 | 서비스명과 일체감 최고, 신비로운 캐릭터 콘셉트 | 게임·브랜드에서 흔히 쓰는 이름이라 상표 충돌 가능성 높음 |
| 3 | **Cue** | 큐 | 음악·방송 용어 "큐(신호)" + 질문(Q) | 음악 서비스에 딱 맞는 의미, 기억하기 쉬움 | 일반 단어라 검색·상표 등록이 어려움 |
| 4 | **Tempi** | 템피 | Tempo의 복수형(이탈리아어) | BPM에 맞춰 춤추는 캐릭터와 잘 맞음 | 평범하게 느껴질 수 있음 |
| 5 | **Riffy** | 리피 | Riff(반복 악구) + -y | 밝고 장난스러운 캐릭터에 어울림 | 영어권에서 가벼운 느낌 |
| 6 | **Nexo** | 넥소 | Nx + 연결(nexus) | 협업·연결 콘셉트 | 자동차·기업명 등 기존 사용 많음 |
| 7 | **Moji** | 모지 | 모듈(module) + 귀여움 | 친근함 | Studio Nx와 연결 약함 |

### 3.3 결정 (2026-10-01) ✅
- 이름: **Nyxi (닉시)** — Studio **Nx** 발음과 이어지는 Nyx에 친근한 -i를 붙인 형태. 위 후보표 2번(Nyx)의 변형입니다.
- 문서·DB 전체에 반영 완료 (`user_settings.character_code` 기본값 `'nyxi'`).
- Nyx 계열 이름은 게임·브랜드에서 쓰인 사례가 있어, **최종 확정 전 상표 검색**(KIPRIS·USPTO)과 도메인·SNS 계정 확인을 권장합니다.
- **캐릭터 외형·콘셉트·애니메이션은 별도 AI 플랫폼에서 제작**하므로 이 프로젝트 문서에서는 다루지 않습니다. 이 프로젝트는 제공받은 에셋을 표시하는 **연동 규격**(PRD 02 FR-288)만 정의합니다.

## 4. 캐릭터를 아이콘·도우미 얼굴로 쓰는 방식 (적용됨)
> FL Studio의 **Fruity Dance**는 FL Chan이 박자에 맞춰 춤추는 플러그인입니다. Studio Nx는 같은 아이디어에 **도우미 역할**을 더합니다.

| 상태 | 언제 | 캐릭터 창 | 상단바 아이콘 |
|---|---|---|---|
| 대기 (idle) | 정지 상태 | 숨쉬기·두리번 | 정지 얼굴 |
| 춤 (dance) | 재생 중 | **BPM 동기 춤** (Fruity Dance식) | 박자에 맞춰 살짝 까딱 |
| 생각 중 (thinking) | 도우미 답변 생성 중 | 고민하는 동작 + "…" | 로딩 표시 |
| 말하기 (talking) | 답변 완료 (패널 닫힘) | 말풍선에 답변 요약 | 배지(●) |
| 리액션 (react) | 저장·출력·분리 완료, 새 코멘트 | 짧은 기쁨/놀람 동작 | — |
| 안내 (guide) | 튜토리얼 진행 | 말풍선 + 화살표로 UI 가리킴 | — |

- 캐릭터 창을 숨겨도 **상단바 아이콘은 항상 남아** 도우미 버튼 역할을 합니다.
- 필요한 에셋(**별도 AI 플랫폼에서 제작해 제공**): 상태 6종 애니메이션, 아이콘 24·32·48px, 디바이스 카드 아트(디바이스 종류별 + 바이패스 변형), `manifest.json`. 규격은 PRD 02 FR-288.
- 디바이스 카드 UI(PRD 02 §4.7.1)도 같은 에셋을 바탕으로 합니다 — 카드에는 핵심 노브만, 세부 설정은 카드 클릭 시 상세 설정 모달.

## 5. 템플릿 적용 확인창 (적용됨)
확인창이 뜨는 3곳과 예시입니다. 서버 API도 `confirmed=true` 없이는 거부합니다.

| 위치 | 상황 |
|---|---|
| ① 새 프로젝트 → [템플릿으로 시작] | 생성될 내용 확인 |
| ② 작업 중 프로젝트 → [템플릿 적용] | 추가 / **교체** 선택, 교체 시 경고 + 자동 스냅샷 |
| ③ AI 분석 결과 → [이 레퍼런스로 새 프로젝트] | AI가 만든 구성 확인 |

```
┌ 템플릿 적용: "Lo-fi Chill" ─────────────────────┐
│ 적용 방식: (●) 추가 — 기존 트랙 유지   ( ) 교체      │
│                                              │
│ 변경 내용                                     │
│  • BPM 120 → 82,  키: 없음 → A minor           │
│  • 트랙 4개 추가: Drums, Keys, Bass, Vinyl FX     │
│  • 마스터: Limiter → Tape Sat + Limiter         │
│                                              │
│ ⓘ 적용 후 Ctrl+Z 한 번으로 모두 되돌릴 수 있어요     │
│                              [취소]  [적용]     │
└──────────────────────────────────────────────┘
교체 선택 시: ⚠ "기존 트랙 6개가 삭제됩니다. 적용 직전 상태를 스냅샷으로 자동 저장합니다."
```

## 6. 패턴 도입으로 바뀐 데이터 구조 (적용됨)
제안 2.4(패턴·링크 클립)를 적용하면서 **MIDI 노트가 저장되는 위치가 바뀌었습니다.** 구현 전에 꼭 알아두실 부분이라 정리합니다.

```
변경 전:  tracks → clips → midi_notes            (노트가 클립에 속함)
변경 후:  tracks → clips ─(pattern_id)→ patterns → midi_notes
                                   (노트는 패턴에 속하고, 클립은 패턴을 "가리킴")
```
| 동작 | 처리 |
|---|---|
| 새 MIDI 클립 만들기 | 새 패턴 1개 + 클립 1개 생성 |
| **링크 복제** (Ctrl+D) | 클립만 새로 만들고 **같은 pattern_id** → 노트 수정 시 모두 반영 |
| **독립 복제** (Ctrl+Shift+D) | 패턴 + 노트를 복사해 새 pattern_id |
| 고유하게 만들기 | 해당 클립만 패턴 복사본으로 교체 |
| 클립 삭제 | 클립만 삭제. 그 패턴을 쓰는 클립이 하나도 없으면 패턴도 정리 |

- **1단계(MVP)부터 이 구조로 만들어야** 나중에 링크 복제·클립 런처를 붙일 때 DB 이전이 필요 없습니다. 그래서 구현 계획 S1-08에 "노트는 패턴에 저장"을 명시했습니다.
- 같은 이유로 **마스터도 트랙**(`track_type='MASTER'`)으로 바꿨습니다. 마스터 디바이스·오토메이션이 일반 트랙과 같은 테이블을 쓰게 되어 코드가 단순해집니다.
